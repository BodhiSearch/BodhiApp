# 20 — Codebase: child-process management and app lifecycle (for `cloudflared` supervisor)

**Date:** 2026-09-15
**Scope:** Where and how to add a `cloudflared` supervisor that starts when the app starts (native/desktop only) and stops when the app exits — modeled on how BodhiApp already manages the `llama-server` child process. Extends `01-bodhi-app-codebase-map.md` (§1, §2) rather than repeating it. All line numbers verified by reading the files on 2026-09-15; re-check if the files have moved.

## a) Pattern to copy: spawning/monitoring/stopping a long-lived child process

Copy `crates/llama_server_proc/src/server.rs` almost directly — it is a self-contained "own and outlive-safely a subprocess" module with no framework dependencies.

| Concern | Where | Notes |
|---|---|---|
| Spawn | `crates/llama_server_proc/src/server.rs:216-221` | `std::process::Command::new(&self.executable_path).args(args).stdout(Stdio::piped()).stderr(Stdio::piped()).spawn()` inside an `async fn start(&self)`. The `spawn()` call itself is sync (std), wrapped in an async fn only so callers can `.await` readiness after it. |
| Own the handle | `crates/llama_server_proc/src/server.rs:100-107` | `process: Mutex<Option<std::process::Child>>` field on the struct — `Option` so it can be `.take()`n on stop, `Mutex` (std, not tokio) because it's only ever locked for a synchronous take/replace, never held across an `.await`. |
| Drain stdout/stderr | `crates/llama_server_proc/src/server.rs:139-163` (`monitor_output`) | Two **`std::thread::spawn`** threads (not `tokio::spawn`) each running a blocking `BufReader::new(pipe).lines()` loop, logging via `tracing`. `Child::wait()` (std) blocks the calling thread until output pipes are drained by the OS or the process exits, so if you don't drain stdout/stderr on separate threads a child that writes a lot of output can deadlock. |
| Readiness wait | `crates/llama_server_proc/src/server.rs:165-189` (`wait_for_server_ready`) | Polls `GET /health` every 1s, up to 300 attempts (5 min timeout: see `crates/llama_server_proc/CLAUDE.md`). For `cloudflared`, there's no `/health` endpoint — the readiness signal is instead a line matched out of stdout/stderr (cloudflared prints the assigned hostname / "Registered tunnel connection" to stderr), so the reader thread needs to notify a `tokio::sync::oneshot` or `watch` channel instead of just logging. |
| Stop | `crates/llama_server_proc/src/server.rs:240-251` (`stop_unboxed`) | Takes the `Child` out of the `Mutex`, calls `process.kill()` (std, sends SIGKILL) then `process.wait()` (std, blocking reap) — both synchronous, called from an `async fn` (fine since they're fast local syscalls, unlike a network call). |
| Guaranteed cleanup | `crates/llama_server_proc/src/server.rs:198-210` (`impl Drop for LlamaServer`) | Same kill+wait, run unconditionally when the struct is dropped — this is the safety net so an orphaned handle (e.g., early return, panic unwind) doesn't leak the child process. **This is the single most important pattern to copy**: whatever owns the `cloudflared` `Child` needs an equivalent `Drop` impl. |
| Trait-object dual-stop | `crates/llama_server_proc/src/server.rs:87-89`, documented in `crates/llama_server_proc/CLAUDE.md` ("Server trait dual-stop methods") | `stop(self: Box<Self>)` for callers holding `Box<dyn Server>`, `stop_unboxed(self)` for direct-struct callers/tests — works around `Box<dyn Trait>` not supporting arbitrary consuming `self` methods. Copy this if the tunnel supervisor is also exposed as `Box<dyn Trait>`. |

**Why `std::process` and not `tokio::process`** (per project memory `feedback_llama_server_proc_std_process.md`, corroborated by the code): the crate is intentionally framework-free (no tokio dependency in its own `Cargo.toml` beyond what's needed for the async trait signatures/reqwest), and `tokio::process::Child` has a known footgun — if the `Child` (and its reaper future) is dropped without an explicit `.wait()`/kill flow, orphaned processes can leak, especially across `tokio::spawn` boundaries and on process shutdown. `std::process::Child` + an explicit `Drop` that calls `kill()+wait()` synchronously is simpler to reason about and guarantees cleanup regardless of what async context drops the owner. **Recommendation: use `std::process::Command`/`Child` for the `cloudflared` child too**, with output-draining on `std::thread::spawn` threads exactly as above, not `tokio::process`.

Nothing in `crates/server_core` re-implements process spawning — `SharedContext` (`crates/server_core/src/shared_rw.rs`) only *owns* a `Box<dyn Server>` (the llama_server_proc trait) behind a `tokio::sync::RwLock<Option<Box<dyn Server>>>` (`shared_rw.rs:77`) and orchestrates start/stop/reload around it (`shared_rw.rs:152-179`). The actual process mechanics stay isolated in `llama_server_proc`. A `cloudflared` supervisor should follow the same split: a low-level `crates/llama_server_proc`-style module owning the `Child`, wrapped by a higher-level service (in `services`, see §d) that owns the `RwLock<Option<...>>` and lifecycle policy.

## b) Where the "start tunnel if enabled" hook belongs

The final bound port is known at two points, both **after** `TcpListener::bind` succeeds:

1. Inside `Server::start_new`, `crates/server_app/src/server.rs:70-73`: `let listener = TcpListener::bind(&addr).await?;` then `ready.send(())` — but this only signals a `oneshot::Sender<()>` (no payload), and this function is deep inside the spawned task, past the point where `serve.rs` computes `server_url`.
2. The caller, `ServeCommand::get_server_handle` in `crates/server_app/src/serve.rs:140-158`: `server_url`/`public_url` are computed from the **requested** `host`/`port` (`serve.rs:140-141`) *before* the bind task is spawned (`serve.rs:143-154`), and only confirmed bound when `ready_rx.await` resolves successfully (`serve.rs:155-159`, `Ok(()) => { println!("server started on server_url=..."); }`). This is the earliest point where you know the bind actually succeeded (not just that a port number was chosen) — **this is the right hook**: add the "start tunnel if enabled" call in the `Ok(())` arm at `serve.rs:156-159`, after the existing `tracing::info!(server_url, public_url, "server started")`. `host`/`port` are already in scope there, and `service.setting_service()` (`serve.rs:121`) is available to read the tunnel-enabled flag and to fetch/persist the tunnel's public hostname.

Since `BODHI_PORT` defaults to a fixed value and is not re-picked per run (see §f), the bound port is deterministic even before this hook runs, but confirming via `ready_rx` guards against the bind failing (e.g., `test_server_fails_when_port_already_in_use`, `serve.rs:191-214`) and only starting `cloudflared` once the app server is actually listening.

`ShutdownLocalLlamaCallback` (`serve.rs:36-49`) is the existing precedent for "a service that needs to react to the server's lifecycle, injected via `AppService`" — a `StartTunnelCallback`/registration could follow the same shape but for *start*, there is no equivalent callback hook (only `ShutdownCallback` exists on `crates/server_app/src/server.rs:26-29`), so the start hook has to be a plain call inserted at `serve.rs:156-159` rather than a trait extension point.

## c) Where "stop tunnel" must run on shutdown

**Serve / container mode** (no Tauri): `ServeCommand::aexecute` → `ServerShutdownHandle::shutdown_on_ctrlc` (`serve.rs:86-91`) blocks on `shutdown_signal()` (`crates/server_app/src/shutdown.rs:3-33`, waits for Ctrl+C or, on Unix, SIGTERM) then calls `self.shutdown()` (`serve.rs:93-100`), which sends on the `shutdown: Sender<()>` oneshot. That oneshot is the `shutdown_rx` awaited inside `axum::serve(...).with_graceful_shutdown(async move { ... })` at `crates/server_app/src/server.rs:74-90`. **This closure at `server.rs:74-90` is the one central shutdown point that already stops llama-server**: after the shutdown signal resolves (`server.rs:75-85`), it runs `if let Some(callback) = callback { (*callback).shutdown().await; }` (`server.rs:87-89`), and the callback passed in is `ShutdownLocalLlamaCallback` (`serve.rs:36-49`), whose `shutdown()` calls `app_service.local_llama().stop()`. **This is the pattern to copy for "stop tunnel"**: either (1) extend `ShutdownLocalLlamaCallback` to also stop the tunnel service, or (2) add a second `Box<dyn ShutdownCallback>` — but `Server::start_new` currently takes only `Option<Box<dyn ShutdownCallback>>` (single, not `Vec`), so either change the signature to `Vec<Box<dyn ShutdownCallback>>` or compose a `CompositeShutdownCallback` that calls both in turn. Note this callback only runs when the shutdown is *graceful* (SIGKILL/crash bypasses it) — so `cloudflared`'s own `Drop` impl (§a) remains the real safety net for ungraceful exits, same as `LlamaServer`'s.

**Native/Tauri mode**: there are **two** separate exit paths, and only one of them actually terminates the process:
- `on_window_event` (`crates/bodhi/src-tauri/src/native_init.rs:154-161`) handles `WindowEvent::CloseRequested` by calling `window.hide()` and `api.prevent_close()` — **closing the window does not quit the app or stop anything** (by design: BodhiApp is tray-resident).
- `on_menu_event`, tray "quit" item (`native_init.rs:163-192`): takes the `ServerHandleState` (`Arc<Mutex<Option<ServerShutdownHandle>>>`, managed via `app.manage(...)` at `native_init.rs:106-107`), calls `handle.shutdown().await` (same `ServerShutdownHandle::shutdown` as serve mode, `serve.rs:93-100`, which triggers the same `server.rs:74-90` graceful-shutdown closure and the same `ShutdownLocalLlamaCallback`), then `app_clone.exit(0)` (or `exit(1)` on error). **This tray "quit" handler (`native_init.rs:163-192`) is the only place a native-mode process actually terminates**, and it is downstream of the same central shutdown closure as serve mode — so extending `ShutdownLocalLlamaCallback` (or adding a composite callback) covers both native and serve/container modes with one change, no Tauri-specific code needed for the *stop* side. (`app.on_window_event` and OS-level SIGKILL/force-quit still bypass this — same caveat as above, covered only by the tunnel struct's own `Drop`.)

There is currently **no** `tauri::RunEvent::Exit` / `AppHandle::exit` hook elsewhere in `native_init.rs`, and no Tauri `before_exit`/`background` listener beyond the tray menu — confirmed by reading the whole file (`crates/bodhi/src-tauri/src/native_init.rs:1-207`, the only `.exit(...)` calls are at `native_init.rs:170,173,186` inside `on_menu_event`).

## d) How a service gets `Arc<dyn SettingService>`/`Arc<dyn AuthService>`/db injected

Follow `crates/lib_bodhiserver/src/app_service_builder.rs` exactly — this is the single wiring point for every top-level service:

1. **Build the service** inside `AppServiceBuilder::build()` (`app_service_builder.rs:78-227`), after the dependency it needs already exists in scope. E.g. `HealthRegistry` (`app_service_builder.rs:204-205`: `Arc::new(services::DefaultHealthRegistry::default())`, no deps) or `DownloadService` (`app_service_builder.rs:207-209`: needs `db_service.clone()`, `time_service.clone()`). A `TunnelService` would similarly be constructed with whatever subset of `setting_service.clone()` / `auth_service.clone()` / `db_service.clone()` it needs — all of these are already `Arc<dyn ...>` in scope by the point `local_llama` is built (`app_service_builder.rs:150-158`, itself a good model: `DefaultSharedContext::new(hub_service.clone(), setting_service.clone())`).
2. **Add a trait method** on `AppService` (`crates/services/src/app_service/app_service.rs:12-58`), e.g. `fn tunnel_service(&self) -> Arc<dyn TunnelService>;` alongside `health_registry()` (line 51) / `download_service()` (line 53).
3. **Add a struct field + accessor** on `DefaultAppService` (`app_service.rs:62-84` struct, `86-170` impl) — the struct derives `derive_new::new` (`app_service.rs:61`), so the constructor is positional and order-sensitive; the new field must be added to the call site at `app_service_builder.rs:212-233`. Separately, the test double `AppServiceStub` (`crates/services/src/test_utils/app.rs:51`, a `derive_builder`-based struct, not `DefaultAppService`) needs its own new `Option<Arc<dyn TunnelService>>` field with a `#[builder(default = "self.default_tunnel_service()")]` attribute — follow the `health_registry`/`download_service` pair there (`test_utils/app.rs:94-97` fields, `260-271` default-builder fns, `579-591` trait-impl accessors that `.expect(...)` if unconfigured).
4. **Register any background loop** the same way `RefreshWorker` is (`app_service_builder.rs:176-186`): `tokio::spawn(async move { worker.run().await; })` called directly inside `build()`, detached (no `JoinHandle` retained, no shutdown wiring — see finding in §e below). If the tunnel supervisor needs an app-lifetime watchdog task, this is the precedent, but note its limitation.

Settings-only additions (new `BODHI_TUNNEL_*` keys) don't need new injection — they go through the existing `SettingService` already injected everywhere, per `01-bodhi-app-codebase-map.md` §2.

## e) How a long-running service exposes status to routes

Three distinct in-process patterns already exist; pick based on what "status" means for the tunnel:

| Pattern | Example | Shape | Fits when |
|---|---|---|---|
| `RwLock<Option<Box<dyn T>>>` — single live resource, replace-on-reload | `SharedContext.server`, `crates/server_core/src/shared_rw.rs:77` | `tokio::sync::RwLock<Option<Box<dyn Server>>>`; readers `.read().await`, writers `.write().await` + `.take()`/replace | The tunnel process itself (one `cloudflared` child, running or not) — this is the direct analog of what you're building, same `is_loaded()`-style boolean check pattern (`shared_rw.rs:147-150`) |
| `RwLock<HashMap<K, V>>` — keyed status registry | `HealthRegistry`/`DefaultHealthRegistry`, `crates/services/src/models/router/health.rs:39-41` | `std::sync::RwLock<HashMap<String, EndpointHealth>>` (note: **std** `RwLock`, not tokio — because all its methods are synchronous, no `.await` inside the critical section) | Multiple independent statuses keyed by ID (not needed for a single per-instance tunnel, but the pattern if you ever track e.g. per-connector status) |
| `Arc<AtomicBool>` shared flag(s) | `InMemoryQueue`/`RefreshWorker` processing flag, `crates/services/src/utils/queue_service.rs:159-177,239-273` | Plain `Arc<AtomicBool>` cloned into both the producer/service and the background worker, `Ordering::Relaxed` load/store | Cheap boolean status (e.g. "tunnel connecting" vs "up") read far more often than written, no async needed |
| DB-backed status (no in-memory struct at all) | Model download progress, `crates/routes_app/src/models/files/routes_files_pull.rs:196-214` (`spawn_pull` → `Progress::Database(DatabaseProgress::new(db_service, tenant_id, request_id))`); `crates/services/src/models/download_service.rs` (`DefaultDownloadService`, no `RwLock`/`HashMap` fields at all) | Background `tokio::spawn`'d task (`routes_files_pull.rs:196`) writes progress straight to a DB row; routes read the same row | Status needs to survive process restart, or be queried historically (not applicable to a single ephemeral tunnel process, but relevant if you want an audit/event log of tunnel up/down transitions) |

**Recommendation**: model the tunnel supervisor's status exactly like `SharedContext` — a `TunnelService` trait (mirroring `SharedContext` at `shared_rw.rs:22-41`: `start`/`stop`/`is_running`/`status()`/`public_url()`) backed by `DefaultTunnelService { child: RwLock<Option<TunnelChild>>, last_url: RwLock<Option<String>>, ... }`, exposed to routes via the `AppService` accessor from §d. This is the closest existing shape to "one long-lived external process this app instance owns, whose live/dead state and last-known metadata (public URL, analogous to the port llama-server bound to) routes need to read."

**Gap worth noting for the design**: `InMemoryQueue`'s `QueueConsumer::shutdown()` (`queue_service.rs:154,236-239`) is never called anywhere in the app — grepped `crates/lib_bodhiserver/src`, `crates/server_app/src`, `crates/bodhi/src-tauri/src` for `.shutdown()` calls and only `ServerShutdownHandle`/`ShutdownCallback` call sites exist (`serve.rs:89,93`; `native_init.rs:168`; `server.rs:88`). The `RefreshWorker`'s `tokio::spawn`'d loop (`app_service_builder.rs:176-186`) is simply abandoned on process exit — acceptable for it (idempotent, resumable, no external side channel to clean up) but **not** an acceptable pattern for `cloudflared`: an abandoned tunnel supervisor task would leak the child process (or leave the tunnel registered at Cloudflare's edge with no owner). Don't copy the `RefreshWorker` "fire and forget, no shutdown wiring" pattern for the tunnel — copy `ShutdownLocalLlamaCallback`'s wiring instead (§c), plus the `Drop` safety net (§a).

## f) How the app picks its listen port, and whether it changes between runs

**It does not change between runs by default** — it's a persisted/overridable setting, not dynamically picked:

- Default: `DEFAULT_PORT: u16 = 1135` (`crates/services/src/settings/constants.rs:33`, also `DEFAULT_PORT_STR = "1135"` at line 34), default host `DEFAULT_HOST: &str = "0.0.0.0"` (`constants.rs:32`).
- Runtime read: `SettingService::port()` (`crates/services/src/settings/setting_service.rs:225-239`) reads the `BODHI_PORT` setting value, falling back to `DEFAULT_PORT` if unset or non-numeric; `host()` similarly reads `BODHI_HOST` (`setting_service.rs:218-223`, `.expect("BODHI_HOST should be set")` — always set since it's a system default).
- `BODHI_PORT`/`BODHI_HOST` resolve through the standard precedence chain (System → CommandLine → Environment → Database → SettingsFile → Default, per `01-bodhi-app-codebase-map.md` §2) — so the actual port used is stable across restarts unless the operator explicitly changes it via the `bodhi serve --port <n>` CLI flag (`crates/bodhi/src-tauri/src/app.rs:12-30`, only available in non-native/server builds), an env var, or the settings file/DB.
- Both native (`native_init.rs:80-81`: `let port = setting_service.port().await;`) and container (`server_init.rs`, same two-line pattern: `host`/`port` from `setting_service`) modes read the exact same setting — there is no OS-assigned ephemeral port (`TcpListener::bind` is always given a concrete `host:port`, never `:0`; contrast with `llama_server_proc`'s own port picking via `portpicker::pick_unused_port()` at `crates/llama_server_proc/src/server.rs:24,44`, which is **only** used for the *internal* llama.cpp server, not the public-facing Bodhi HTTP server).

**Implication for the tunnel**: the Cloudflare named-tunnel ingress config (`cloudflared tunnel ingress` / config.yml `service: http://localhost:<port>`) can be generated once and does not need to be regenerated on every app start merely because the port might have changed — it only needs to change if the operator explicitly reconfigures `BODHI_PORT`. The tunnel's ingress target should read `setting_service.port()` (and `host()`, though `0.0.0.0` won't work as a client-facing target — same `0.0.0.0` → `127.0.0.1` substitution already applied for the browser-launch URL at `native_init.rs:82-86` will likely be needed for the tunnel's local ingress URL too) at the same point identified in §b, not a value cached from an earlier run.

## Summary: concrete shape for the `cloudflared` supervisor

1. `crates/cloudflared_proc/` (new leaf crate, sibling to `llama_server_proc`, same no-framework-deps shape) — owns the `std::process::Child`, `Drop`-safe kill+wait, `std::thread::spawn` stdout/stderr readers that additionally parse the tunnel-connected line and push it through a `tokio::sync::watch` channel for readiness/URL.
2. `services::TunnelService` trait + `DefaultTunnelService` (new module under `crates/services/src/`) — owns `RwLock<Option<...>>` state exactly like `SharedContext`, injected into `AppServiceBuilder::build()` per §d, exposed via a new `AppService::tunnel_service()` accessor.
3. Start hook: `crates/server_app/src/serve.rs:156-159`, inside the `Ok(())` ready-signal arm, gated on `is_native()`/`BODHI_TUNNEL_ENABLED`.
4. Stop hook: extend/compose `ShutdownLocalLlamaCallback` (`serve.rs:36-49`) so the one graceful-shutdown closure at `crates/server_app/src/server.rs:74-90` stops both llama-server and the tunnel — covers both native tray-quit (`native_init.rs:163-192`) and serve/container Ctrl-C/SIGTERM (`shutdown.rs`) paths with no Tauri-specific code.
