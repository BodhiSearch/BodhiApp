# 13 — Cloudflare edge behavior for LLM API traffic through a named tunnel

**Date:** 2026-09-15
**Scope:** Named tunnels only (quick tunnels are out of scope for this feature — see `README.md`). Answers what BodhiApp must configure or warn about when it proxies its OpenAI/Anthropic/Gemini-compatible APIs (including SSE streaming) through a Cloudflare named tunnel to `http://127.0.0.1:<port>`.

Builds on `00-consolidated-research.md` and `bodhiapp-cloudflare-tunnel-feasibility.md`, which already cover quick-tunnel SSE buffering (now moot) and named-tunnel setup basics. This doc corrects one thing from that earlier research: **named tunnels are not automatically SSE-safe either** — the same buffering rule applies, it's just satisfiable because BodhiApp already sends the right header (see §1).

## 1. SSE streaming through named tunnels

**Verdict: streams unbuffered today, and BodhiApp already meets the one condition that requires.**

- `cloudflared`'s documented behavior: *"Proxied traffic through Cloudflare Tunnel is buffered by default unless the origin server includes the `Content-Type: text/event-stream` response header. This header tells `cloudflared` to stream data as it arrives instead of buffering the entire response."* — [Cloudflare Tunnel troubleshooting: common errors](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/troubleshoot-tunnels/common-errors/)
- BodhiApp's SSE responses already set this header: `crates/server_core/src/fwd_sse.rs:20` sets `.header("Content-Type", "text/event-stream")` before streaming the body via `Body::from_stream`. **No code change needed for this specific requirement.** This applies uniformly — quick tunnel and named tunnel share the same `cloudflared` proxy code path, so the rule is not specific to one flavor.
- Historical evidence this was a real, tracked bug (not just a doc note): [`cloudflare/cloudflared#199` "Server-sent-events are buffered"](https://github.com/cloudflare/cloudflared/issues/199) (2020) — an Express app with correct SSE headers and `flushHeaders()` still had its stream buffered through Argo Tunnel. UNVERIFIED: the exact fix/PR that resolved it; the issue thread available to this research had no maintainer resolution comment, but the current docs describe the Content-Type-gated streaming behavior as the present-day contract, and it is corroborated by a second, more recent report scoped to *quick* tunnels and GET requests: [`cloudflare/cloudflared#1449`](https://github.com/cloudflare/cloudflared/issues/1449) (Apr 2025) — SSE over a GET request was not streamed in real time on a Quick Tunnel (POST streamed fine); this is quick-tunnel-specific per the issue title and out of scope here, but is a reminder to test with the actual method BodhiApp uses (`POST /v1/chat/completions`).
- **Recommendation:** don't rely solely on the doc claim — add this to the E2E/manual verification checklist for the tunnel feature (send a streaming chat completion through the live named tunnel and assert chunks arrive incrementally, not as one flush at the end).
- **Compression is not a separate risk to configure around.** Cloudflare does not gzip/brotli `text/event-stream` responses (compression is skipped for streaming/chunked content types at the edge) — UNVERIFIED as an explicit doc statement, but consistent with the "stream as it arrives" behavior above; no BodhiApp-side action needed.
- **Rocket Loader / Auto Minify are irrelevant** — both only rewrite `text/html` responses (Rocket Loader touches `<script>` tags in HTML pages; Auto Minify's HTML/CSS/JS modes act on those content types). BodhiApp's API responses are `application/json` or `text/event-stream`, neither touched. Only relevant if these are ever left on for the *UI* HTML pages served through the same hostname — no functional risk to the API paths either way.

### `originRequest` settings — recommendation for BodhiApp's tunnel config

Full parameter reference: [Cloudflare One — origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/).

| Parameter | Default | BodhiApp recommendation | Why |
|---|---|---|---|
| `connectTimeout` | `30s` | Leave default | TCP connect to `127.0.0.1` is instant; irrelevant to LLM prefill latency (that's response time, not connect time). |
| `tcpKeepAlive` | `30s` | Leave default | Loopback connection, no NAT/firewall to keep alive for. |
| `keepAliveTimeout` | `1m30s` | Leave default | How long `cloudflared` keeps an idle connection to the local service open; fine for request-response API traffic. |
| `keepAliveConnections` | `100` | Leave default | Max idle keepalive connections `cloudflared` pools to the local origin; 100 is generous for a single-instance app. |
| `noHappyEyeballs` | `false` | Leave default | Loopback IPv4/IPv6 fallback logic is irrelevant at `127.0.0.1`. |
| `http2Origin` | `false` (HTTP/1.1 to origin) | Leave default (`false`) | BodhiApp's Axum/Hyper server serves plain HTTP/1.1 over loopback; no origin-side TLS exists for `http2Origin`'s h2-over-TLS requirement anyway (see §6). |
| `disableChunkedEncoding` | `false` | **Leave default (`false`) — do not set `true`** | `true` is documented for WSGI servers that can't stream; it would defeat the chunked/streamed transfer Axum's `Body::from_stream` relies on for SSE (`crates/server_core/src/fwd_sse.rs:19-25`). Setting this to `true` would very likely reintroduce buffering. |
| `noTLSVerify` | `false` | N/A — origin is `http://`, not `https://` | Only matters when the origin URL is `https://`; BodhiApp's origin is plaintext loopback (§6). |
| `proxyType` | `""` | Leave default | Only used for SOCKS5 origin proxying; not applicable. |
| `httpHostHeader` | `""` (preserves original) | Leave default | See §6 — the incoming public `Host` (the tunnel's public hostname) is preserved and forwarded to the origin by default, which is exactly what BodhiApp's canonical-URL middleware expects to see. |

**Net:** none of the `originRequest` knobs need to be touched for correct SSE/API behavior — the defaults are already right for a loopback HTTP/1.1 origin, and the one real gotcha (`Content-Type: text/event-stream`) is already satisfied by existing code.

## 2. Timeouts: is a >100s non-streaming LLM request at risk?

Cloudflare's proxy timeout stack (client↔edge and edge↔origin) is **not one single "100 second rule"** — the widely-cited 100s figure is a community/anecdotal number, not what current official docs state. Official documented values ([Connection limits](https://developers.cloudflare.com/fundamentals/reference/connection-limits/)):

| Leg | Timeout | Notes |
|---|---|---|
| Client ↔ Cloudflare edge, HTTP/1.1 keep-alive | 400s | |
| Client ↔ Cloudflare edge, HTTP/2 idle | 400s | |
| Cloudflare edge ↔ origin, TCP connect | ~19s hard cap (`connectTimeout` in tunnel config caps this from the tunnel side too) | |
| Cloudflare edge ↔ origin, TCP ACK | 90s | |
| Cloudflare edge ↔ origin, **proxy read timeout** | **125s** (this is the practical "first byte / idle-between-bytes" limit; not adjustable except on Enterprise) | This is the one that bites a long, non-streaming LLM completion with a large prefill and no bytes sent until the full response is ready. |
| Cloudflare edge ↔ origin, proxy write timeout | 30s | |
| Cloudflare edge ↔ origin, proxy idle timeout | 900s | Applies once bytes are flowing (keeps a connection open between requests / between chunks). |

- The docs explicitly redirect tunnel users elsewhere for these: *"If you are using Cloudflare tunnels, refer to Origin configuration to view or modify your connection settings."* — i.e., the `originRequest` table in §1 is the tunnel-specific override surface; there is **no documented way to raise the 125s proxy-read timeout for cloudflared origins** short of Enterprise cache-rule tuning of `proxy_read_timeout` (up to 6000s), which is a **zone-level Cache Rule feature, Enterprise-only**, and not something a self-serve/Free/Pro user can access. UNVERIFIED: whether that Enterprise Cache Rule setting even applies to Tunnel-sourced traffic (it's documented for regular reverse-proxy origins) — do not assume it as a mitigation without re-verifying on a real Enterprise zone.
- Practical consequence exceeding 524 "A timeout occurred" ([Error 524 docs](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/)): a non-streaming `/v1/chat/completions` (`stream: false`) with a very large prompt prefill (or a slow/cold local model) that produces **zero response bytes for >~100–125s** will hit a 524 at the Cloudflare edge, even though the local llama.cpp process is still working and would have eventually returned 200. The connection between `cloudflared` and Cloudflare's edge is unaffected (tunnel stays up) — this is strictly an edge→client response-timing problem.
- **Mitigation for BodhiApp:** this is a strong argument for defaulting to (or documenting a recommendation for) **streaming mode when accessed via the tunnel hostname**, since the first SSE byte can be flushed quickly (e.g., an empty/heartbeat chunk) well inside the timeout window, and each subsequent chunk resets the idle clock. A raw non-streaming request with a large prefill has no such mitigation available to a Free/Pro/Business user. Document this as a known limitation in the tunnel feature's UI copy (e.g., "for prompts likely to take longer than ~100s to first token, use streaming (`stream: true`)").
- No official Cloudflare doc frames this as a "keep-alive comment" pattern (that's an application pattern from SSE frameworks, e.g. sending `: ping\n\n` periodically) — but it is directly applicable and consistent with the "each byte resets idle timer" mechanics above. UNVERIFIED against an explicit Cloudflare statement; inferred from the documented idle-timeout mechanics.

## 4. Caching & security defaults that could break the API

| Feature | Default state | Risk to BodhiApp API | Action |
|---|---|---|---|
| **Cache (by content type)** | Cloudflare does **not** cache `text/html` or `application/json` by default; default caching is driven by file extension for static assets plus `Cache-Control`/`Expires` response headers when present | Low — JSON API responses are not cached unless BodhiApp's own `Cache-Control` headers say so, or the user adds a Cache Rule. [Default cache behavior](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/) | No action; if BodhiApp ever adds cache-control headers to API responses, verify they say `no-store`/`private` for anything user- or session-specific. |
| **Bot Fight Mode (Free)** | **Off by default**, opt-in toggle | **High, if the user enables it.** It's a single global zone toggle with **no exemption mechanism** — *"Cannot be customized, adjusted, or reconfigured via WAF custom rules... You cannot bypass or skip Bot Fight Mode using WAF custom rules or Page Rules"* because it runs outside the Ruleset Engine, and Cloudflare's own docs warn it *"may challenge API or mobile app traffic."* This will very plausibly challenge/block the OpenAI Python/Node SDK, `curl`, and other non-browser HTTP clients hitting `/v1/chat/completions` through the tunnel hostname — with **no way to allowlist the path on Free**. [Get started with Bot Fight Mode](https://developers.cloudflare.com/bots/get-started/bot-fight-mode/) | **Document prominently**: do not enable Bot Fight Mode on the zone/hostname used for the tunnel, or accept that API clients will be blocked. |
| **Super Bot Fight Mode (Pro+)** | Off by default | Same category of risk, but **fixable**: runs on the Ruleset Engine and supports **Skip rules**, so a Pro+ user can exempt `/v1/*`, `/anthropic/v1/*`, `/v1beta/*` API paths by path-match Skip rule. | If instructions are written for Pro+ users, include a sample Skip rule for the API path prefixes. |
| **Managed WAF rules** | Not auto-applied to a new zone by default; the user must explicitly enable/deploy a Managed Ruleset (free "Cloudflare Free Managed Ruleset" exists but is opt-in) | Low by default, but if a user does turn on WAF managed rules, some rules could false-positive on request bodies containing prompt text (e.g., SQLi-pattern false positives on code snippets in prompts) | Note as a "if you enable WAF, watch for false positives on `/v1/chat/completions` request bodies" caveat; UNVERIFIED specific rule IDs — would need to test against a real deployment. |
| **Rate limiting rules** | Pro plan and above only (not available on Free); none configured by default even on paid plans | N/A on Free (feature doesn't exist); on Pro+, no default rule exists until the user creates one | No action needed unless documenting Pro+ hardening options. |
| **Browser Integrity Check** | UNVERIFIED default state — could not confirm from official docs in this pass; it is a legacy/simpler check than Bot Fight Mode and is generally described as low-friction (JS/header heuristics, not a CPU challenge) | Low-moderate — could reject clients with unusual/missing headers | Recommend leaving off for API hostnames; call out as UNVERIFIED-default in the doc for the user to check in their dashboard (SSL/TLS → Edge Certificates or Security settings, depending on dashboard version). |
| **Email obfuscation / HTML rewriting (Scrape Shield)** | Scoped to `text/html`/`application/xhtml+xml` responses only, by Cloudflare's own implementation | None for the API — JSON responses aren't touched. Only relevant to the UI's HTML pages served on the same tunnel hostname, and only if the UI happens to render an email address as literal text. | No action for API traffic. |
| **HTTPS-only + HSTS** | New zones auto-manage SSL/TLS mode ("Automatic" default); **"Always Use HTTPS" is not on by default**; **HSTS is not enabled by default** — both require explicit user action in Edge Certificates settings | Moderate — without "Always Use HTTPS", plain `http://<tunnel-host>` requests are allowed through to the edge (then likely fail/behave oddly reaching a tunnel that's TLS-terminated at the edge) rather than being redirected | Recommend the setup instructions tell the user to enable "Always Use HTTPS" for the tunnel's hostname; HSTS is optional hardening, not required (and risky to recommend blindly since it's sticky in browsers). |
| **Cloudflare Access (Zero Trust) fronting the hostname** | Optional, not part of the core feature | N/A (opt-in hardening only, per the task's own framing) | Free tier covers **up to 50 users** at no cost ([Cloudflare Free Plan / Zero Trust plans](https://www.cloudflare.com/plans/zero-trust-services/); reported consistently across secondary sources, UNVERIFIED against the primary pricing page snapshot at research time). For API clients, pair an Access application with a **Service Token** policy: the self-hosted app can accept `CF-Access-Client-Id` + `CF-Access-Client-Secret` headers (or a single custom header) so non-interactive SDK/CLI clients skip the SSO redirect that would otherwise break the OpenAI-SDK-style bearer-token flow. [Service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/). Document as optional hardening in a "secure your tunnel further" section, not a setup requirement — this is an extra auth layer *in front of* BodhiApp's own OAuth2/JWT, not a replacement. |

## 5. Headers Cloudflare adds / what BodhiApp must trust

Reference: [HTTP request headers](https://developers.cloudflare.com/fundamentals/reference/http-request-headers/).

| Header | Purpose | Relevance to BodhiApp |
|---|---|---|
| `CF-Connecting-IP` | Real client IP as seen by Cloudflare's edge | Trustworthy for a tunnel-only ingress (cloudflared is outbound-only; there's no other path to the origin that could spoof this before it reaches the edge). Not currently read anywhere in BodhiApp (`grep` for `cf-connecting-ip` under `crates/` found nothing) — worth using this, not `X-Forwarded-For`, if/when BodhiApp adds IP-based audit logging or rate limiting for tunnel traffic. |
| `X-Forwarded-For` | Chain of proxy/visitor IPs | Same trust caveat: first entry is the real client only because Cloudflare is the sole front door; don't trust if the app could also be reached directly (it currently can be, via loopback/LAN — but a request bearing this header could then only originate from something already on the trusted local network, since public ingress is tunnel-only). |
| `X-Forwarded-Proto` | `http` or `https` as seen by the visitor at the edge | **Already read** by `crates/routes_app/src/middleware/redirects/canonical_url_middleware.rs:80-90` (`extract_scheme`), which is exactly what a tunnel needs: the tunnel terminates TLS at Cloudflare's edge and speaks plaintext HTTP to BodhiApp's loopback origin (§6), so without trusting this header BodhiApp would think every tunnel request is `http` and could build wrong `https://` redirect/callback URLs. This header is set by Cloudflare itself at the edge (not by `cloudflared`), so it's safe to trust for tunnel-only ingress. |
| `CF-Ray` | Per-request trace ID (`<hash>-<PoP-code>`) | Useful to log for support/debugging tunnel issues; not currently consumed anywhere in the codebase (greenfield). |
| `CF-Visitor` | JSON `{"scheme":"https"}` — legacy/alternate way to learn the visitor's scheme | Redundant with `X-Forwarded-Proto`; no need to also read this. |
| `Host` | The public hostname the visitor requested | See §6 — passed through by `cloudflared` (`httpHostHeader` default `""`). Already what the canonical-URL middleware reads via `header::HOST` (`canonical_url_middleware.rs:43-53`) to compare against `BODHI_PUBLIC_HOST`. **This means `BODHI_PUBLIC_HOST` should be set to the tunnel's public hostname** for the canonical-redirect logic to treat tunnel requests as already-canonical (not redirect-loop them) — flag this as an implementation requirement, not just a nice-to-have. |

**Net for BodhiApp:** the existing canonical-URL middleware's trust model (read `x-forwarded-proto`/`x-forwarded-scheme`, fall back to URI scheme; read `Host` header directly) is **already correct** for sitting behind a Cloudflare named tunnel — no middleware code change is required, only a settings/config requirement to point `BODHI_PUBLIC_HOST`(and `BODHI_PUBLIC_SCHEME=https`) at the tunnel hostname when the tunnel is enabled.

## 6. Origin protocol: plaintext loopback is standard, confirmed

- Standard and recommended `cloudflared` setup for a local, non-TLS backend is `cloudflared tunnel run` (or `ingress:` config) pointing `service:` at `http://127.0.0.1:<port>` (or `http://localhost:<port>`) — TLS termination happens at Cloudflare's edge; `cloudflared` then speaks plain HTTP to the local service. This matches BodhiApp's default `http://` loopback server (`BODHI_SCHEME=http`, `BODHI_HOST`/`BODHI_PORT`) with **zero origin-side TLS setup required**. The `noTLSVerify` / `originServerName` config knobs only come into play if the `service:` URL is itself `https://` (e.g., a locally self-signed cert) — not BodhiApp's case.
- **Host header:** `originRequest.httpHostHeader` defaults to `""`, meaning `cloudflared` **preserves and forwards the original `Host` header from the public request** (the tunnel's public hostname, e.g. `myapp.example.com`) to the local origin — it does not rewrite it to `127.0.0.1:<port>`. This is what makes `canonical_url_middleware.rs`'s `Host`-header check (§5) work correctly out of the box: BodhiApp sees the public hostname, not the loopback address, in the `Host` header of tunneled requests.

## Open items for the implementation plan

1. Decide whether streaming should be *recommended* or *enforced* (e.g., a 524-prevention warning, or actually rejecting very-long-prefill non-streaming requests with a client-facing error) for requests routed through the tunnel hostname specifically — since this is a Cloudflare edge limitation, not a BodhiApp one, it only applies when `Host` matches the tunnel hostname, not on loopback/LAN access.
2. Setup instructions must tell the user: (a) don't enable (Super) Bot Fight Mode without an API-path Skip rule (Free plan: don't enable it at all on that hostname), (b) enable "Always Use HTTPS" for the hostname, (c) set `BODHI_PUBLIC_HOST`/`BODHI_PUBLIC_SCHEME` to the tunnel hostname/`https`.
3. Re-verify the exact upload-size-by-plan table and the Browser Integrity Check default against Cloudflare's own dashboard/docs before hard-coding either into user-facing copy — both are flagged UNVERIFIED above.
4. If BodhiApp later adds tunnel-aware audit logging or IP-based rate limiting, use `CF-Connecting-IP`, not `X-Forwarded-For`.
